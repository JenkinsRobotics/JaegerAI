No runtime change, install, build/update/restart on the runtime Mac, deployment, default merge or remote write is authorized or executed by this preparation. Existing app implementation and all work must be preserved. Product remains PARTIAL.

1. Finish fresh scoped/broad qualification, package proofs and independent exact-byte archive acceptance. Obtain separate authorization naming exact target/version, downtime and permitted operations. Never bypass browser, filesystem or transport restrictions.
2. Before any separately approved deployment, freshly inventory current runtime source, installed packages, served UI and backend assets, and ALL dirty/untracked runtime-local UI/backend work under authorized read-only access. Current runtime state is unverified and previously differed from the review source. Do not assume this branch contains every runtime-local edit. Protect complete recoverable backups, verify restoration in isolation, reconcile or port local edits into an isolated checkout, review the result and run affected tests before proposing deployment. No blind overwrite/reset.
3. Protect chats, knowledge, configuration, credentials, pending tasks/approvals, asset files/index/Board and database journals using access-restricted restorable backups. Never include them in source or public evidence. An actively changing database file copy is not verified consistent backup. Preserve receipt identities/schema versions and validate isolated restore.
4. Review matching backend/client protocol rollout. New backend rejects old blind writes with 428; malformed/stale preconditions give400/409. Existing valid Board files remain readable. Validate new client against exact new backend; do not downgrade writes. Preserve unresolved mounted drafts before reload or service changes. No safe-retry or durable-navigation-draft promise.
5. Rehearse with synthetic or separately authorized protected data. Confirm concurrency, current-state deletion and compatibility alongside source/package/served UI identities. Cross-file asset transaction crash recovery is unresolved; decide explicitly whether that remaining risk is acceptable before rollout.
6. Only after specific approval, use a controlled maintenance boundary and approved install procedure. Retain prior code/packages and a compatible restoration path. Confirm exact source, installed packages, served UI/backend identities, health and authenticated behavior, not installer success alone. Validate existing chats/knowledge, identities, permissions, approvals and new isolated operation without replaying uncertain effects. Provider/audio/external sends need their own scope.
7. On regression preserve new data/diagnostics and stop new work only within approved authority. Assess schema AND protocol compatibility. Older code may read new files while removing CAS protection, so code rollback is not automatically safe. Prefer isolated recovery/reconciliation where necessary. Never restore an old data backup over newer work, reset identities, delete journals or replay unknown effects to make rollback appear successful.
8. Report exact versions/evidence and remaining failures. Build success, package integrity or successful rollback does not mean the whole product is finished.
